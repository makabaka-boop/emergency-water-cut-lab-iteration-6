# 暴雨断管 · 应急供水韧性评估

纯前端单页应用（React + TypeScript + Vite）：载入供水管网 JSON，核算**基线最大供水量**，
并在残量网络中定位**源侧到汇侧的割项**（瓶颈）；随后可逐项停用管段做断管演练，实时得到
**当前供水量、相对损失与新割项**；清空方案精确回到基线。无任何后端与在线调用，全部计算在浏览器内完成。

## 快速开始

```bash
npm ci                # 安装依赖（需 Node 20+）
npm run dev           # 本地开发（Vite 开发服务器）
npm test              # Vitest 全量测试
npm run build         # 类型检查 + 生产构建（输出 dist/）
npm run verify        # 一次性验收：typecheck + 测试 + 构建
```

### Docker Compose

```bash
WEB_PORT=8080 docker compose up --build web   # 通过 WEB_PORT 发布页面（默认 8080）

```

`verify` 服务依次执行 `tsc --noEmit`、`vitest run`、`vite build`，任一失败即非零退出。

## 输入契约

输入为一个 JSON 文本，解析后**必须**是仅含以下四个字段的对象（缺一不可、多一不可）：

```json
{
  "nodes":   [{ "id": "n1" }, ...],
  "arcs":    [{ "id": "a1", "from": "n1", "to": "n2", "capacity": 100 }, ...],
  "sources": [{ "node": "n1", "capacity": 100 }, ...],
  "sinks":   [{ "node": "n2", "capacity": 80 }, ...]
}
```

校验规则（任一不满足即判 `INVALID_NETWORK`，页面保留上次模型）：

| 规则 | 说明 |
| --- | --- |
| 顶层结构 | 对象，恰好包含 `nodes` / `arcs` / `sources` / `sinks` 四个数组 |
| 节点 id | 非空字符串，节点间互不重复 |
| 管段 | `id` 非空字符串且管段间互不重复；`from` / `to` 必须指向已声明节点 |
| 供需项 | `node` 必须指向已声明节点；`sources` 内、`sinks` 内各自不重复（同一节点可同时是供水点与需求点） |
| 容量 | 整数，`0 ≤ capacity ≤ 10^12`（管段、供水、需求一致） |
| 容量总和 | 管段 + 供水 + 需求全部容量之和 `≤ 9×10^15`（小于 2^53，保证全程精确整数运算） |
| 规模 | 节点 `≤ 10000`，管段 `≤ 50000` |
| 重边 / 反向边 | 合法；自环合法（对流量无贡献） |

## 载入来源与交错控制

文件、文本草稿、当前模型与演练状态保持**一致且可见**的来源关系：

- **文件内容同步进文本框**：选择文件读取成功后，文件内容先同步进文本框再解析——
  文本框始终展示当前模型的来源内容，「解析文本框内容」不会静默回退到旧草稿；
  文件内容非法时同样同步，错误详情对应文本框中可见的输入，可直接对照定位、
  修正后重新解析。
- **来源可见**：当前模型统计行标注来源（文件「文件名」/ 内置示例 / 文本框）；
  错误横幅标注被拒绝输入的来源；文本框被手动修改后与当前模型不一致时，
  页面明确提示「尚未解析」。
- **读取失败即 `INVALID_NETWORK`**：文件读取失败（拒绝的 Promise）同样转为
  `INVALID_NETWORK` 并在详情中点名文件与原因；模型、停用集合、需求点选择与
  联合承诺全部保留。
- **最后一次操作决定结果**：编辑草稿、解析文本、载入示例或选择新文件，都会使
  在途的文件读取作废；迟到的读取结果（无论成功或失败）被整体丢弃，不覆盖
  用户最后一次明确操作。读取 / 解析失败只更新错误，不改变模型与演练状态。

## 计算口径

**建模**：超级源 → 每个供水点（容量 = 供水能力）；原管段（停用管段从当前网络移除）；
每个需求点 → 超级汇（容量 = 需求能力）。最大供水量 = 该网络的最大流（Dinic 算法，
残量用 Float64 存储；因流量总和 ≤ 9×10^15 < 2^53，全程为精确整数）。

**割项**：在最大流残量网络中从超级源遍历，取「源侧可达集 → 汇侧不可达集」的建模边：

- 供水点割项：供水点节点不可达（其供水边饱和），`id` 取节点 id；
- 管段割项：起点可达且终点不可达（该管段饱和；容量 0 的越界管段同样列入，容量记 0），`id` 取管段 id；
- 需求点割项：需求点节点可达（其需求边饱和），`id` 取节点 id。

割项按 **类别（供水点 → 管段 → 需求点）、id 的 UTF-16 编码单元升序** 排列
（即 JavaScript 字符串默认 `<` 比较）。割项容量之和恒等于最大供水量。

**断管演练**：停用集合为空时的核算结果即基线。每停用/恢复一条管段，对当前网络整体重算：
当前值 = 新最大供水量；绝对损失 = 基线 − 当前；相对损失 = 绝对损失 / 基线
（基线为 0 时约定相对损失为 0）。算法与排序完全确定，**清空方案后重算结果与基线逐项相等**。

### 避难点供水区间

工程师可在基线核算与断管演练面板中从当前模型的需求点里**选择一个**，页面在
**当前最大供水总量不变**的前提下显示该需求点可获水量的三个值：

- **最小可获水量** / **当前 Dinic 方案** / **最大可获水量**。

当前 Dinic 方案值只是总值固定下的**一组可行分配**，并非唯一答案；区间端点在
容量约束、节点守恒与总值（`analysis.value`）均不变时均可实现。

算法（残量环流）：最大流层按**输入边身份**为每条建模边提供该组解的正反残量
容量（`flow` 与 `residual = capacity - flow`；重边、原生反向边、自环、零容量边
以及同一节点兼作供水点与需求点时，各输入边仍独立核算）。对目标需求边 e=(v→T)：

- 增加：辅助残量网络中求超级汇 T → 需求节点 v 的可调流，上限为 e 的正残量
  `c_e − f_e`，沿 T…→v 推送后经 e 的反残量闭合环流，`max = f_e + up`；
- 减少：求 v → T 的可调流，上限为 e 当前流量 `f_e`，`min = f_e − down`。

两个辅助网络都**排除目标需求边自身的正反残量弧**。区间端点不会突破容量、节点
守恒或当前 `analysis.value`。停用/恢复管段后，已选需求点按新断管集合与当前总量
重算；清空方案恢复其基线区间；载入新模型使旧选择失效（落回首个需求点并清除旧
区间）；辅助求解失败时就地提示并清除旧区间，**不影响已成功的基线与演练结果**。
现有输入契约、最大供水量、割项、损失与复核报告结构保持不变。

### 联合最低供水承诺

断管演练面板中，工程师可同时为**多个需求点**填写最低供水量承诺，每项可留空；
填写值须为 **0 至该点容量的整数**（小数、负数、超容量、科学计数等均为无效填写）。
页面随**填写、停用/恢复管段、清空方案**自动重新裁决，**载入新模型时清空承诺**。

裁决必须针对**同一组边流量**：在容量约束与原网络节点守恒成立、且超级源到超级汇
的总量**严格等于当前 `analysis.value`** 的条件下，判断全部下限能否**同时**满足。
因此既不能把单点区间拼接（各点 0..5 不代表可同时取 3、3），也不能只比较承诺
总和与总量（共享管段等局部瓶颈会在承诺和未超总量时否决）。可行时页面**只显示
「可同时兑现」与固定总量，不输出任何逐边/逐点分配**；不可行时明确提示
**联合约束不满足**；无效填写或辅助求解异常只清除联合裁决并就地提示，基线、
当前演练、停用集合与既有单点区间保持可用。

算法（固定总量的下界可行环流）：给每条建模边 e 置下界 l_e（被承诺的需求边
取下限，其余为 0），另加一条超级汇 T → 超级源 S 的**汇到源回边**，其下界与
上界都固定为当前总量 V——于是任何可行环流中 S→T 的总量都被锁死为 V。把各边
下界按 `b[v] = Σ入边下界 − Σ出边下界`（含回边的 V）折算为节点失衡：
`b[v] > 0` 加辅助源 SS → v、容量 b[v]；`b[v] < 0` 加 v → 辅助汇 TT、容量
−b[v]；其余边以剩余容量 `c_e − l_e` 加入辅助网络。再求一次 SS → TT 最大流，
**当且仅当全部失衡边饱和**（最大流值 = 辅助源总供给；Σb ≡ 0 保证供需总量相等）
时，所有下限可同时兑现。停用管段按既有 `PlanEdge` 输入身份移除；重边、原生
反向边、自环、零容量边以及同一节点兼作供需的边，仍按各自输入身份独立建模。
该辅助网络与单点区间无关，直接从原始容量与下界构造，一次 Dinic 求解完成，
**10000 节点 / 50000 管段的一次联合校验在 4 秒内完成**。输入契约、Analysis、
复核报告结构与 WEB_PORT 发布方式均保持兼容。

### 最小承诺缺口诊断（显式提交）

当多项最低承诺无法同时兑现时，仅返回「不可行」不足以指导调度。断管演练面板中
工程师可在同一张承诺表上填写下限，**显式点击「运行诊断」**提交一次「最小承诺
缺口诊断」（opt-in；不运行时所有交互与原来完全一致）。诊断在

> 总送水量仍**严格等于当前网络可达最大值**（`analysis.value`）

的全部最大流方案中，选出各安置点未达承诺量之和最小的一组，返回：

- **总缺口**（全部被承诺点的未达量之和，已压到最小）；
- **逐点实际供水量与缺口**（未承诺点只给实际供水，缺口恒 0）；
- **完整流量见证**：每条管段/供水/需求边的流量，返回前自检满足全部容量与
  节点守恒，总量严格等于最大值。

诊断绝不把各点单独可达上限拼成一份虚假联合方案：每一次改道都是当前最大流残量
网络中的环流，见证始终是**同一组边流量**上的可行最大流。

**算法（残量环流，三阶段 + 富余裁决，见 `core/gap.ts`）**：设当前 Dinic 最大流
为 f（总量 V），任意同值最大流与 f 之差是残量网络中的环流（与避难点区间同一
原理），全程在副本上进行，**不改写 `solvePlan` 的 flow/residual**。

1. **阶段 B（最小化总缺口）**：冻结全部被承诺需求边自身残量弧，代之以门节点 G、
   补给弧 v_k→G（容量 = 尚欠单位 d_k−f_k）与富余弧 T→v_k（容量 = 超过承诺、
   可无偿调走的单位 f_k−d_k；未承诺点的真实反残量弧天然开放）。求 T→G 最大流，
   门节点收到的总量即承诺满足总量的最大增量（从已满足点调水只能走富余弧，容量
   保证其不跌破承诺，杜绝「先损后补」的虚假增量）。
2. **阶段 C（满足量字典序裁决）**：按需求点顺序逐点永久冻结更早承诺边、临时
   排除自身边，在 T→v_k 上限额（补到承诺）推送，使逐点满足量
   s_k = min(供水量, 承诺) 字典序最大。
3. **阶段 D（富余水裁决）**：缺口与满足量已定后，剩余无法避免的富余来水按同样
   顺序继续优先分给更早承诺点（捐赠者只准动用承诺之外的富余），使**逐点实际
   供水量向量也唯一**。算法边序固定，相同最优值得出逐项相同、可复现的见证。

零承诺点无可补单位、天然缺口 0；不可达需求点没有 T→v 残量路，缺口原样保留。
任何无效填写或辅助/自检异常只返回失败并就地提示，**不抛出、不污染最大流、
联合承诺裁决与停用管段状态**；返回前统一校验容量、原节点守恒、超级源汇平衡
（恰为 V）与逐点缺口。

**同一份已提交结果**：页面摘要、逐点实际供水/缺口表、割项表与管段清单的网络
着色、以及「导出诊断见证 JSON」全部读取同一次点击提交的不可变结果。承诺填写或
停用管段在运行后被改动时，结果标记为**已过期**并停止着色，重新运行后刷新——
不会让算法结果、摘要与着色显示成不同版本。着色口径：蓝=有流量未饱和管段/
已满足需求点，橙=饱和瓶颈管段，红=未达承诺的需求点。

### 单管复通建议（显式生成）

暴雨抢修只能先复通一条已停用管段时，调度员需要知道**哪一条最能缩小安置点
承诺缺口**，再决定是否真的改动演练方案。断管演练面板中点击「生成复通建议」
（opt-in；不生成时所有交互与原来完全一致）后，从当前停用管段中按 id
（UTF-16 升序）取**至多 20 条候选**，每条候选分别在**互不污染的方案副本**
上恢复一条（`solvePlan` 重新建模，不改写当前方案的 flow/residual 与停用
集合），并沿现有三条数据流求出该候选自身的结论：

- **最大流**：复通后网络的最大总供水量；
- **联合承诺**：复通后全部承诺能否同时兑现；
- **最小承诺缺口**：复通后在「总送水量 = 复通后最大值」约束下的最小总缺口
  与完整流量见证。

候选按 **总缺口最小 → 总供水量最大 → 管段 id（UTF-16 升序）** 稳定排序，
页面展示各候选相对当前方案的差额（供水量差额恒 ≥ 0、缺口差额恒 ≤ 0：恢复
管段只扩大可行域，且同一网络内总量越大可达最小缺口越小）。**建议与见证都
不是已应用结果**；「采用并复通」前逐项核对生成建议所依赖的**模型、停用集合
与承诺**（规范指纹），任一变化即判**过期**并拒绝——过期建议不得覆盖现场
新操作，确认失败保留原方案与报告。明确结果覆盖全部边界：无停管（无候选）、
候选无改善（推荐为空，建议保持当前方案）、无承诺（缺口恒 0，按供水量排序）、
复通后最大流改变（逐候选供水差额与汇总条数）。计算失败同样保留原方案与报告。
原断管切换与导出契约不变。

## 独立复核

基线面板与演练面板各自独立展示，并可分别导出**复核报告 JSON**（自包含，可脱离页面重算验证）：

```json
{
  "report": "baseline | drill",
  "generatedAt": "ISO-8601 时间戳",
  "network": { "nodes": [], "arcs": [], "sources": [], "sinks": [] },
  "disabledArcIds": ["..."],
  "maxSupply": 0,
  "cut": [{ "kind": "source | arc | sink", "id": "...", "capacity": 0, "from": "...", "to": "..." }],
  "loss": 0,
  "relativeLoss": 0
}
```

复核方式：用同一 `network` 与 `disabledArcIds` 按上文「计算口径」重算，
`maxSupply` 与 `cut` 应逐项一致，且割项容量之和等于 `maxSupply`。

## 测试与验收

Vitest 覆盖（`tests/`）：

- `exhaustive.test.ts`：300 个随机小图（多源多汇、零容量、重边、反向边、自环、随机断管）
  **穷举全部割集**，验证 最大供水量 = 最小割容量，割项与「由流量独立重建残量网络」的结果逐项一致，
  并校验流量可行性（容量约束、节点守恒）与割项排序；
- `interval.test.ts`：**避难点供水区间**。枚举小整数网络（2..4 节点、容量 0..3，
  天然覆盖重边/原生反向边/自环/零容量/供需同点/随机断管）的**全部可行流**，
  筛出总值等于最大流的方案，逐需求点核对区间上下界与端点可实现性、当前分配落内；
  并用独立的辅助环流构造端点流复核容量、守恒与总值不变；
  锁定共享瓶颈为 5、下游两需求点容量各 5 时二者区间均为 0..5 且当前分配落内；
  含零容量、单点退化、停用重算、清空回基线、失败结果与
  **10000 节点/50000 管段单次查询 4 秒内**等用例；
- `commitment.test.ts`：**联合最低供水承诺**。枚举小整数网络在**固定最大总量下的
  全部可行流**作为预言机，对每个需求点「留空 / 0..容量」的全部承诺组合逐一核对
  联合裁决（含重边/原生反向边/自环/零容量/供需同点/随机断管）；锁定共享容量 5
  时 d1、d2 各承诺 3 虽分别落在 0..5 区间仍不可行；加入独立向 d3 供水 5 使总量
  为 10，证明承诺和 6 未超总量时局部瓶颈仍会否决；覆盖断管重算、清空恢复、
  无效填写与辅助求解异常的失败隔离，以及 **10000 节点/50000 管段一次联合校验
  4 秒内**；
- `gap.test.ts`：**最小承诺缺口诊断**。用枚举小整数网络（2..4 节点、容量 0..3，
  天然覆盖重边/原生反向边/自环/零容量/供需同点/随机断管）的**全部可行流**作为
  穷举预言机，对每个需求点「留空 / 0..容量」的全部承诺组合（数千组）逐一核对
  最小总缺口与逐点实际供水的字典序裁决；并对每份见证**独立校验全部管段容量、
  节点守恒、超级源汇平衡恰为最大值、逐点水量与见证一致**；锁定共享瓶颈各承诺 3
  时缺口压到 1 且裁决 (3,2)、承诺 2/2 多个同优方案稳定裁决 (3,2)、冗余路径断管、

  无偿调走；验证「总缺口 0 ⇔ 联合裁决可行」、诊断不改写方案 flow/residual、
  断管重算/清空恢复、空承诺与见证边身份一一对应、无效填写与异常的失败隔离、

## 目录结构

```
src/
  core/
    types.ts      数据契约（网络 / 割项 / 核算结果）
    validate.ts   JSON 解析与全部校验规则
    maxflow.ts    Dinic 最大流（类型化数组、迭代阻塞流；按输入边身份提供 flow/residual）
    analyze.ts    建模、割项提取与排序、相对损失、完整方案解（边身份+残量）
    interval.ts   避难点供水区间（残量环流：增/减目标需求边的可调流）
    commitment.ts 联合最低供水承诺（固定总量的下界可行环流 + 辅助源汇饱和检查）
    gap.ts        最小承诺缺口诊断（残量环流三阶段 + 富余裁决；完整容量/守恒见证）
    restore.ts    单管复通建议（≤20 候选独立副本评估、缺口/供水量排序、指纹过期确认）
    loader.ts     载入状态机（来源一致性 + 交错控制；失败保留上次模型）
    sample.ts     内置示例网络
    format.ts     整数 / 百分比展示格式化
  App.tsx         单页界面（载入 / 基线 / 演练三个独立面板）
tests/            Vitest 全量测试
Dockerfile        deps → verify / build → web 多阶段
docker-compose.yml  web（WEB_PORT 发布）+ verify（一次性验收）
```
